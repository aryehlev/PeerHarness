For teams that work in Claude Code

Your team votes on how its AI coding agents behave.

You correct your coding agent. PeerHarness turns the correction into a one-sentence rule. Keep it for your own agent, or propose it to your team: once a majority approves, every member's agent follows it.

Set it up Read the source

Early and not audited. For Claude Code on macOS. On Linux it works from a terminal, without the windows. Windows is not supported. Read the limits before you rely on it.

§ 1 · Try it in Claude Code

Say it to your agent.

Start a new Claude Code session and say these, one at a time. You need no teammate for it.

  1. “From now on, use pnpm here, not npm.”

    Your agent notes the rule (“Use pnpm, not npm, in this repository.”) and tells you it did. It does the same when you correct it in the middle of work.

  2. “Keep it.”

    A window shows the exact rule. Click Proceed: the rule is installed for your own agent, which reads it from its next session. Nothing is shared.

  3. “Create a PeerHarness team called acme.”

    You are its only member for now.

  4. “Propose the pnpm rule to acme.”

    A window shows the exact text that would leave your machine. Click Proceed: the rule is put to your team's vote.

  5. “Vote approve on it.”

    A window shows your ballot. Click Proceed: one of one members approved, so the rule passed and is now your team's.

Agents suggest, people decide.

Your agent can note a rule and open a window on your screen that shows the exact text. It cannot answer the window: inside its session, keeping a rule, sharing one, voting, inviting and joining take your click. Every window has two buttons, Cancel and Proceed, and Cancel is the default.

That stops an agent that is trying to help. It is not a sandbox.

Then ask what is new

“What is in my PeerHarness inbox?” lists the rules your agent noted and the proposals that wait for your vote. “Anything new in PeerHarness?” exchanges with the other members first.

And add a teammate

Dana asks her agent for her device key and sends it to you. You say “Invite Dana to acme. Her device key is ed25519:…” and click Proceed in a window that names her device. She joins with your node's peer id and the team's fingerprint, which you tell her by phone or in person. From then on a rule needs both of your votes, and so does admitting a third member.

§ 2 · The vote

A majority of everyone, and nobody's veto.

  • One person, one vote, however many devices they have.
  • A majority of everyone entitled to vote. Not voting counts as not approving. Nobody has a veto: a reject is recorded with its reason and does not block.
  • No deadlines and no coordinator. A member cannot withdraw an approval, and counting reads no clock, so two nodes that hold the same records always agree.
  • Membership is voted too. Admitting or removing a member and changing the thresholds need a vote. The founder's key signs the resulting charter, and nodes refuse any charter that a passed vote does not justify.
  • A passed rule takes effect. It is installed for every member's agent, and any member can opt out of a single rule on their own machine.

No vote and no charter can switch these off

  1. Nothing leaves your machine without you seeing the exact text and confirming it.
  2. PeerHarness never executes a rule. A rule is one instruction-only SKILL.md; tool pre-approval and shell-injection syntax are refused outright.
  3. No vote grants read access.
  4. A rule with high-risk content is never installed without asking you.
  5. You can refuse a rule and you can leave.

§ 3 · No server

Every node counts for itself.

There is no server. Each person runs their own node with their own keys, and every node checks every signature and counts every vote for itself.

The founder's key signs the charter that a vote produced. It cannot stand in for the vote.

§ 4 · Set it up

Paste this into Claude Code.

Set up PeerHarness for me: https://github.com/aryehlev/peerharness

1. Install it:
   curl -fsSL https://raw.githubusercontent.com/aryehlev/peerharness/main/install.sh | sh
2. The next step is mine. It is where I allow what you may start for me, so do not
   run it yourself: it would be refused. Ask me to run this in my own terminal:
   ~/.local/bin/peerharness setup

Then tell me to start a new Claude Code session, and what I can ask you there.

Your agent installs it

The install line downloads the release binary for your machine, checks it against the release's SHA256SUMS and puts it in ~/.local/bin. No sudo, and nothing else is changed.

You run setup, once

It is where you allow what your agent may start for you, so your agent is refused it. It creates your key and database and connects PeerHarness to Claude Code: two hooks, one skill and its tools. It shows each change before it makes it and asks you to confirm.

What it stores

One hook keeps a redacted copy of each prompt you type, so that corrections can be noticed. The copies stay on your machine, for 14 days by default, in a database that is not encrypted.

Then start a new Claude Code session and try it. More: what setup adds and stores, and how to take it out again.

§ 5 · Limits

What it does not do.

PeerHarness is early and has not been audited. Read these before you rely on it.

  • The agent guard is not a sandbox. A session is recognized by an environment variable, and only Claude Code's by default. A process running as you that hides it can run the same commands with --yes. Your agent chooses when a window appears: reading it before you click is your part.
  • A rule is text that your agent acts on, and your agent can run commands. The risk scanner and the redaction are heuristics. Read a rule as you would a script.
  • Joining installs rules you have not read. The join window shows the charter and how many rules it carries, not their text. You can opt out of any afterwards.
  • The founder can revoke a device without a vote, for a lost laptop. Its ballots stop counting, so a result that needed one is undone. The founder's key also signs every change of the roll: if it is lost, nobody can be admitted or removed.
  • No secret ballot, and at most 64 members. A member who never votes makes every threshold harder to reach.
  • A node is reachable only while a daemon runs: yours, or the one your agent runs while its session is open. There is no background service yet.
  • Internet mode shows your node's public key and IP address to servers run by volunteers.

The full list is in docs/limits.md, and how each part was checked in docs/checked.md.

Why not a CLAUDE.md in git?

If the rule is about one repository and your team already reviews pull requests, commit the file. You need nothing else.

PeerHarness is for rules that follow people across repositories, for groups with no shared repository or nobody who administers one, and for members who want to see the exact text they vote on and to opt out of a rule alone.

It is also more dynamic and more democratic. A rule starts as a correction in the middle of work, with no file to edit and no pull request to open. And it passes by a majority of everyone, not by the say of whoever can merge.
