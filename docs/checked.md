# What was checked, and how

This is the table behind [What works today](../README.md#what-works-today) in the
README. The README has the summary and the runs of the whole suite. This page says,
part by part, what a test covers, what was run by hand and what was never tried, and
at its end what followed the pre-launch check.

*Tested* means an automated test covers it. *By hand* means a run during development
that [decisions.md](decisions.md), the README's history or the pre-launch check
records, on the version named. *Not tried* means no run is recorded.

The pre-launch check is the one the README names: a check of 0.4.0 made with AI
coding agents on 2026-11-10, which [decisions.md](decisions.md) calls the launch
audit. Its report is not in the repository. What this page and the ADRs say it ran is
all that is published of it.

Where each threat of the security model is tested, test by test, is in the last
section of [security-model.md](security-model.md#test-coverage).

| Part | How it was checked |
|---|---|
| Voting: charter, roll, proposals, ballots, results, amendments, repeal | tested. A `proposal create` whose key does not unlock leaves the note and the library as they were, and nothing is proposed (`a_proposal_that_could_not_be_signed_leaves_its_candidate_as_it_was`) |
| One person's loop: `note`, `keep`, `review`, `skills install` and `uninstall` | tested |
| Creating a node (`init`) | tested: a second `init` for the same home is refused while one runs, and one that fails leaves the home as it found it, a configuration file that was there included. These tests were run on Linux only so far. By hand on Linux, on a pseudo-terminal: the first `init` waiting at its passphrase prompt, the second refused, the first then failing and leaving nothing. Not tried: macOS, where the keychain asks in place of the prompt, and a file system without locks. Two limits are known, and the code was not changed for them ([ADR-045](decisions.md)): a configuration file that is a link is replaced by a regular file, and two inits that race and both fail can leave an empty home directory |
| Circle life: create, invite, join, remove, leave, amend, devices, revoke, questions, opt-outs | tested, with separate nodes. Leaving: with a passphrase that does not unlock the key, the circle's rule is removed from the machine and nothing is signed; a second run makes the request; a request that is on record, the member's own or another member's removal of them, is not made a second time, by a first run after `--undo` either (`leaving_again_after_an_undo_makes_no_second_request`, `a_first_leave_names_a_members_removal_that_is_on_record_and_signs_nothing`); a removal on record that would also drop a rule is named as another proposal, and the member's own request is made (`a_removal_that_would_also_drop_a_rule_is_not_reported_as_the_request_to_leave`); a member who was voted off the roll leaves with no key used and gets the same report (`leaving_when_already_off_the_roll_reports_like_every_other_leave`). That a first run signs the request it previewed or none has unit tests only (`a_first_leave_decides_about_its_request_before_it_asks`, `a_leave_request_is_signed_only_as_it_was_previewed`), and so has that it makes no second request when a member's removal of the leaver arrives while they are asked (`a_request_that_arrived_while_the_owner_was_asked_is_not_made_a_second_time`); by hand, see the next row. A second run of `circle leave` first removes a rule the first run could not remove, also with a passphrase that unlocks nothing, and inside a session it is refused with the rule still there (`leaving_names_what_it_left_in_place_and_a_second_run_tries_again`). Opt-outs: with a passphrase that unlocks nothing, on a node where a vote passed without its result, `rule opt-out` and `proposal refuse` remove the rule, `rule opt-in` installs what was confirmed, and nothing is signed (`an_opt_out_changes_the_machine_before_any_key_is_asked_for`); `--announce` with such a key reports what was done on the machine and is refused (`an_announcement_that_cannot_be_signed_says_what_was_done_on_the_machine`). No test for: `circle leave` from a revoked device, which previews a request it cannot make (by hand in the fourth review; not changed), and a founder's root key that fails after the device key unlocked (not tried) |
| What you are shown before a ballot on an amendment, in a terminal | tested, with separate nodes and stock commands: a device proposed for another member, new thresholds, an admission that would drop or bring back a rule, and an approval refused until the text of a carried rule is on the node. A node that joined without a rule the charter carries: the approval of an amendment that leaves the rule out is refused, and so is the approval of an honest one that keeps it; no window opens for either (`an_amendment_that_drops_an_unheld_rule_is_never_a_ballot_for_a_window`, which runs both, debug builds on unix); the node drafts no amendment of its own, and its `circle leave` changes the machine and makes no request, so that a rule repealed since is not brought back. The amendment that leaves the rule out is signed with a member's key, as a modified client signs it. A yes signs what was shown: a stand-in window imports a newer charter, or a rule that passed, before it answers Proceed, and neither the request to admit nor the approval is signed (debug builds on unix). No test for: the same at a prompt in a terminal or at a passphrase prompt while a second process changes the node. The suite has no pseudo-terminal; that the check comes after the key is unlocked has unit tests only (`a_draft_is_put_to_the_vote_only_while_the_node_would_still_draft_it`, `a_repeal_and_a_stance_are_signed_only_for_the_rule_that_was_shown`). By hand on 2026-11-11, on Linux, with a debug build, on a pseudo-terminal, with the key in an encrypted file and an `events import` from a second process while the prompt waited: a rule arriving at the y/N prompt and at the passphrase prompt of `circle remove`, `amend`, `device add`, `invite` and `proposal vote <admission> approve`, a newer charter at the passphrase prompt of `circle remove`, a second `circle leave`, `rule repeal`, and `rule opt-out --announce` each ended with exit 3 and nothing signed; a first `circle leave` left the machine, made no request and signed nothing, also on a node that lacked a carried rule whose records arrived at the prompt. The third review had run the same at the passphrase prompt before that fix, where an amendment and a deciding approval were signed ([ADR-041](decisions.md), "After a third review"). The fourth review ran these cases again and nothing was signed. After its fixes, again by hand on a pseudo-terminal on Linux: `rule opt-out` with no passphrase in the environment had removed the rule while the passphrase prompt still waited, and it stayed removed after Ctrl-C; a first `circle leave` with a member's exact removal of the leaver imported at the y/N prompt, and at the passphrase prompt, made no second request. By hand in the fourth review and not changed: a charter that admits a member, imported at the prompt of `proposal create`, `rule repeal` and `question send`, left the count in the preview (approvals needed, members who can read) one charter behind what was then signed, with the text as shown ([ADR-041](decisions.md), "After a fourth review"). Not tried: macOS, where the keychain may ask in place of the passphrase prompt. The two amendments the pre-launch check crafted by hand, and an amendment that lists a second proposal under the name of a rule in force, are unit tests with hand-signed events |
| A vote and the skills you already have | tested, with three separate nodes: a rule named like PeerHarness's own skill, signed the way a modified client can, is never installed, and a rule kept with `keep` is neither replaced nor removed by a vote on its name. A yes counts for the rule that was shown: a stand-in window imports a newer rule of the same name before it answers Proceed, and nothing is installed. `proposal adopt` is refused then. The way out of a hold is followed step by step in two states. With a rule held in a project, the copy a vote installed for every project cannot be taken out with `skills uninstall`, as the person or in a session. In a project, a copy a vote installed there is refused in the same way, with and without `--scope`, while a copy the owner installed in another project is theirs to remove (`a_voted_copy_in_a_project_is_not_taken_out_by_skills_uninstall`); and where the skill that holds a rule in a project is another circle's voted rule, the command the hold names is refused and names that circle, whose opt-out then lets the held rule be adopted (`the_way_out_of_a_hold_does_not_take_out_another_circles_rule_unasked`). A skill that cannot be removed keeps its record, is reported and is tried again: a unit test (`a_skill_that_cannot_be_removed_stays_on_record_and_is_tried_again`, unix), and through the binary for a copy in a project, whose skills directory the test turns into a link that leads out of the project (`leaving_names_what_it_left_in_place_and_a_second_run_tries_again`); by hand on Linux with a file made unchangeable (`chattr +i`) while its owner left the circle. When the owner takes such a leftover out with `skills uninstall`, the vote's record goes with it, and the same text installed by the owner afterwards survives the next import, after a repeal and after an opt-out (`a_record_of_a_vote_goes_with_the_copy_its_owner_takes_out`). `skills uninstall` refuses a copy of a rule its owner follows, and not one of a rule that no longer binds them: a member voted off the roll, and a member who left, in a project and in the user's directory (`a_copy_of_a_rule_that_no_longer_binds_its_owner_is_theirs_to_take_out`). A voted copy that its owner edited is left in place and named, in the user's directory and in a project, and the command the line names takes it out (`leaving_names_what_it_left_in_place_and_a_second_run_tries_again`), also where `circle mode` or `rule opt-in` is the first command to settle after the repeal, and a `rule opt-out` names another rule it installs (`a_command_that_settles_says_what_it_did_to_other_rules`); an opt-out, a repeal, a moved scope and the wording inside a session are a unit test (`a_voted_copy_that_was_edited_is_left_in_place_and_named_once`), and were run by hand through the binary. No test for: the same race at the prompt of `rule opt-in`, which needs a terminal and a second process (a unit test covers where the confirmation is counted), a hold caused by another circle's rule in the user's skills directory, and the refusal in the user's directory of a copy the owner installed themselves while the rule lives in a project (by hand in the fourth review; not changed). The first two were run by hand in the second review, on Linux with a debug build: at a real prompt on a pseudo-terminal, a newer rule of the same name and a repeal each gave the refusal and left the opt-out in place; and the way out of a hold caused by another circle's rule was followed through the binary. Not reproduced: a rule that takes the name while `proposal adopt` applies the rules; a unit test covers which sentence it then says |
| What a session is refused beyond the windows: `rule opt-in`, `export --local`, a plaintext `init`, a file path given to the join tool, a join that cannot be put in a window | tested, the first three with each of the two session variables. The join by peer id is tested against a private stand-in network, which sees no connection and no lookup from the session's command and does see the same command run by the person; with windows allowed and no window on the machine, the join tool is refused the same way (not on macOS). No test for: the prompt of `rule opt-in` on a real terminal, which the tests answer with `--yes` |
| Exchange by address over QUIC, by shared directory, by file | tested, with separate processes. A line or record file that is not strict JSON is refused, and a join from a file that holds several circles takes the one whose fingerprint you gave: both tested. That a held or waiting rule is reported once per exchange has unit tests only. A daemon prints each hold once per run: tested for a hold that a peer's push created, with three separate processes and a daemon that has no sync interval and knows no peer (`a_daemon_that_only_answers_tells_a_hold_that_a_push_created_once`); for a hold that the daemon's own exchange finds, unit tests only (`a_daemon_prints_a_hold_with_one_report_and_no_later_one`, `a_daemon_tells_a_hold_once_when_it_is_new`). What such a daemon prints for a rule that a push installed, removed or left waiting for its owner: tested with three separate processes, each line once over four pushes (`a_daemon_that_only_answers_tells_what_a_push_installed_and_what_waits`), and a unit test (`a_daemon_tells_what_a_push_changed_and_each_state_once`). By hand on 2026-11-11, on Linux, with debug builds: two daemons over QUIC on loopback, for four ticks of 30 seconds after a peer's push made a rule held on one of them. After the third review's change, again by hand: two daemons where a later report was printed for new events, with one hold line where the third review had counted two, and a daemon that dials nobody, with and without `--sync-every 30`, with one hold line after a push. ## The pre-launch check and the runs of the suite

The pre-launch check ran the whole suite on 2026-11-10, on Linux, at commit `e6fae27`
(0.4.0): 843 tests passed, none failed, and 10 were skipped because they need
multicast, the public network or the real OS keychain. The finding ids that
[decisions.md](decisions.md) cites are the report's own.

Findings of that check were then fixed. A review of the fixes found more, and those
were fixed. A second review found more again, and so did a third and a fourth. What
the fourth found was fixed in part: what was left is listed as not done under "After
a fourth review" in ADR-041, ADR-042 and ADR-045. A fifth review, of the code and of
the documents, found no case in which something was signed, installed or removed
that its owner had not been shown, and three things that a command did not say;
those were changed (ADR-042, "After a fifth review"). Tests were added each time, and
the changes are recorded in ADR-041 to ADR-045 of [decisions.md](decisions.md). All
five reviews were made with AI coding agents, like the check and like the fixes.
Each ran what it reports with a debug build on Linux, in temporary homes. Where a
row above says "by hand in the second review", that is the run it means. The third
and the fourth review, and the fixes that followed each, also ran commands at real
prompts on a pseudo-terminal. Those runs are by hand: the suite has no
pseudo-terminal, and their outputs are not in the repository.

After the fixes for the first review the suite was run on Linux on 2026-11-11, on the
tree of commit `f1c7997`: 932 tests passed, none failed and the same 10 were skipped.
After the fixes for the second review it was run at commit `95830ff`: 947 passed,
none failed and the same 10 were skipped. After the fixes for the third review it
was run at commit `daab3d7`: 961 passed, none failed and the same 10 were skipped.
After the fixes for the fourth review it was run at commit `6431fa6`: 972 passed,
none failed and the same 10 were skipped. That is a run of the whole suite at the
last of those commits; each commit before it was checked with `cargo fmt`, `cargo
clippy` and the tests of the files it touches. The run after the changes for the
fifth review is the one the README gives. CI
runs the same suite on Linux and macOS. No run on macOS is recorded for any of the
fixes.

One test was found to fail now and then, and was changed: the control of
`a_join_nobody_can_be_asked_about_goes_nowhere_near_the_network` waited for a
connection that the stand-in network forgets when it closes, and the third review
saw its file fail 2 times in 18 runs. The control now waits for a question the
stand-in network keeps. After that change the file was run 25 times in a row on
Linux, 10 of them under load, and passed each time.
