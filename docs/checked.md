# What was checked, and how

This is the table behind [What works today](../README.md#what-works-today) in the
README. The README has the summary and the runs of the whole suite. This page says,
part by part, what a test covers, what was run by hand and what was never tried.

*Tested* means an automated test covers it. *By hand* means a run during development
that [decisions.md](decisions.md), the README's history or the pre-launch check
records, on the version named. *Not tried* means no run is recorded.

The pre-launch check is the one the README names: a check of 0.4.0 made with AI
coding agents on 2026-11-10, which [decisions.md](decisions.md) calls the launch
audit. Its report is not in the repository. What this page and the ADRs say it ran is
all that is published of it.

Where each threat of the security model is tested, test by test, is in the last
section of [security-model.md](security-model.md#test-coverage).

| Part | How it was checked |
|---|---|
| Voting: charter, roll, proposals, ballots, results, amendments, repeal | tested |
| One person's loop: `note`, `keep`, `review`, `skills install` and `uninstall` | tested |
| Creating a node (`init`) | tested: a second `init` for the same home is refused while one runs, and one that fails leaves the home as it found it, a configuration file that was there included. These tests were run on Linux only so far. By hand on Linux, on a pseudo-terminal: the first `init` waiting at its passphrase prompt, the second refused, the first then failing and leaving nothing. Not tried: macOS, where the keychain asks in place of the prompt, and a file system without locks |
| Circle life: create, invite, join, remove, leave, amend, devices, revoke, questions, opt-outs | tested, with separate nodes |
| What you are shown before a ballot on an amendment, in a terminal | tested, with separate nodes and stock commands: a device proposed for another member, new thresholds, an admission that would drop or bring back a rule, and an approval refused until the text of a carried rule is on the node. A node that joined without a rule the charter carries: the approval of an amendment that leaves the rule out is refused, no window opens for it, and the node drafts no amendment of its own. That amendment is signed with a member's key, as a modified client signs it. The two amendments the pre-launch check crafted by hand, and an amendment that lists a second proposal under the name of a rule in force, are unit tests with hand-signed events |
| A vote and the skills you already have | tested, with three separate nodes: a rule named like PeerHarness's own skill, signed the way a modified client can, is never installed, and a rule kept with `keep` is neither replaced nor removed by a vote on its name. A yes counts for the rule that was shown: a stand-in window imports a newer rule of the same name before it answers Proceed, and nothing is installed. The way out of a hold is followed step by step in two states. Not tried: the same race at the prompt of `rule opt-in`, which needs a terminal and a second process (a unit test covers where the confirmation is counted), and a hold caused by another circle's rule, through the binary |
| What a session is refused beyond the windows: `rule opt-in`, `export --local`, a plaintext `init`, a file path given to the join tool | tested, the first three with each of the two session variables. Not tried: the prompt of `rule opt-in` on a real terminal, which the tests answer with `--yes` |
| Exchange by address over QUIC, by shared directory, by file | tested, with separate processes. A line or record file that is not strict JSON is refused, and a join from a file that holds several circles takes the one whose fingerprint you gave: both tested. That a held or waiting rule is reported once per exchange, and a hold not at all by a daemon that exchanged nothing, has unit tests only: it was not run with a daemon over QUIC. After a revocation an import can go wrong: see the next row |
| A node left on an old charter after a revocation ([Known limits](../README.md#known-limits)) | no test. By hand on 2026-11-11, on Linux, with a debug build of this tree, encrypted-file keystores and a shared directory, in a circle of four with one device revoked: the node stayed on charter 3, and a second import changed nothing. After `reset` and `init` its join was refused. The amendment that would add its new key needs 3 of 4, and only two members had a device that still counted. On a copy of the home, deleting only the database, then `init` and `circle join`, joined at charter 4 with the same key ([ADR-044](decisions.md)). Not tried: the OS keychain, a node in several circles, the same over QUIC |
| Exchange across the internet (`--internet`) | tested against a private stand-in network. By hand on the real network on 2026-11-10, before v0.1.0, from one machine with both ends behind the same router. Not tried: two different routers, IPv6, Linux |
| Finding members on a local network (`--lan`) | its tests need real multicast, so they do not run in CI and are run by hand, on macOS so far. Not tried on Linux |
| Noticing corrections by itself | best effort. Your agent reports a correction when it notices one. The built-in detector recognizes corrections that name a tool to use or avoid (46 of 70 in our test set, none of 52 ordinary prompts), not whole-sentence rules such as "always run the tests first". You can always write the rule down yourself |
| Deciding in a window from inside Claude Code | macOS only. Tested with a stand-in window: keeping a rule, proposing, voting, inviting and joining. By hand on macOS 14.2, before v0.1.0: the real window opened, closed unanswered and refused a text that does not fit. Not tried: clicking its buttons. Joining in a window fits a circle of up to about five members on a laptop screen |
| The same steps as tools (`peerharness mcp`) | tested with a scripted client, a stand-in window and a stand-in network. By hand before v0.2.0, with Claude Code 2.1.322 on macOS, a stand-in window and a private network in place of the public one ([ADR-038](decisions.md)): asked in plain words, it read the device key, founded a circle, invited someone and kept the node reachable. Three runs, not a measure of how often an agent gets it right. No run with a real agent of noting, keeping, proposing, voting or joining is recorded. Other MCP clients: not tried |
| Being told that a vote waits (`daemon --notify`, and the end-of-turn line in Claude Code) | `--notify` is macOS only. Tested with separate processes and a stand-in notification. By hand, once: macOS accepted the real notification, and whether the banner shows depends on your notification settings for Script Editor. The timer of `--sync-every` has no test beyond its argument |
| Setting up (`peerharness setup`, and the prompt in [Set it up](../README.md#set-it-up)) | tested with a stand-in for Claude Code's `claude` command: it creates the node, connects the agent, registers the tools, changes nothing on a second run and is refused inside an agent's session. Without windows it ends with what works from the terminal, tested on Linux. A home whose settings allow windows, run where none can be shown: it says what still runs and how to turn that off, tested on Linux. By hand: the three `claude mcp` commands it relies on, against Claude Code 2.1.322 with a throwaway configuration. Not tried: the prompt through an agent |
| Taking it out (`reset`) | tested: it explains first, deletes only when a person confirms, refuses a home that is a link, and afterwards lists the folder of each skill that is still installed |
| The install script and the release binaries | the script is tested against a stand-in release: a matching checksum installs, a changed archive does not. In the pre-launch check, on 2026-11-10, the script installed the v0.3.0 x86_64 Linux binary in a container: the checksum matched, and the binary ran `demo` and two processes voting over QUIC on loopback. The aarch64 Linux binary has not been run. For the macOS binaries the last run on record is of v0.2.0. No release of 0.4.0 exists to check |
| The two-process demo script (`demo/two-peers.sh`) | tested on Linux with the binary of this tree named by `PEERHARNESS_BIN` and a `cargo` that fails if it is called. Not tried with a release binary |
| Windows | not supported |
